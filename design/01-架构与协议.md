# Octopus Relay · 架构与协议设计

> 面向个人的轻量级自建中转服务：单二进制 NativeAOT、零外部数据库、纯 JSON 状态持久化、兼容 Octopus 官方中转协议并扩展免浏览器 Access Key 直连。

## 1. 架构与安全边界

```text
桌面 Octopus ──┐                                ┌── 主机 Octopus (Mac / Win / Linux)
               ├── HTTPS / WSS（外层传输加密） ──┤
手机 Octopus ──┘    [内层: SIGMA 端到端加密]      └── 局域网不可达时经中转建立隧道
                         │
              ┌──────────▼──────────┐
              │ Caddy / Nginx / CF  │  TLS 终结 + WebSocket 透传
              └──────────┬──────────┘
                         │ http://127.0.0.1:8080
              ┌──────────▼──────────┐
              │    octopus-relay    │  单进程 NativeAOT（零外部依赖）
              │  RelayHub + 单人鉴权 │  挂载 /data (secret.key + state.json)
              └─────────────────────┘
```

### 两道门，各管一件事
1. **中转鉴权（本服务负责）**：决定“这台设备属于本机主，可以使用我的带宽并通过中转发现我的主机”。
2. **设备配对与端到端加密（Octopus 两端负责）**：每次连接经 SIGMA 握手（ECDH P-256 临时密钥 + ECDSA P-256 设备身份签名 + AES-256-GCM 逐帧加密），中转服务**永远只看到密文帧与字节大小**，不持有任何设备私钥，无法解密终端/对话/文件，也无法代替已配对设备执行任何命令。

## 2. 持久化（纯 JSON，无数据库）

所有状态存放在 `--data`（默认 `./data`，Docker 为 `/data`）目录中，权限在 Unix 下自动设为 `0600`：

| 文件 | 内容 | 写入策略 |
|---|---|---|
| `secret.key` | 48 字节随机签名主密钥（base64），未传 `RELAY_SECRET` 时首次启动自动生成 | 原子写一次，重启复用，确保未过期 `oa1.*` 访问令牌重启后仍有效 |
| `state.json` | 单机主信息（PBKDF2-SHA256 密码哈希、可选 Access Key 的 SHA-256 哈希）、已授权设备表（公钥 + 单次轮换 `refreshHash`）、Web 会话表、按月流量统计 | `state.json.<rand>.tmp` → `fsync` → 原子 `rename` 覆盖；流量计数 30 秒节流落盘并在进程退出时强制刷盘 |

## 3. 协议端点总览

### 3.1 能力探测（自建扩展 / Relay v2）

`GET /v1/info`

```json
{
  "protocol": 2,
  "mode": "self-hosted",
  "name": "Octopus Relay",
  "version": "1.1.0",
  "auth": ["device_code", "access_key"],
  "transports": ["ws", "quic"],
  "stunServers": ["stun:relay.example.com:3478"],
  "quicEndpoint": "quic://relay.example.com:8443"
}
```

- `protocol: 2` 向后兼容所有校验 `protocol >= 1` 的老版本客户端；客户端连老服务若收到 `404`，仍自动回退到标准 `device_code` + WebSocket 流程。
- `stunServers`：启用内置 UDP STUN（`RELAY_STUN_PORT`）或配置 `RELAY_STUN_SERVERS` 时下发，供客户端与主机进行公网 WebRTC P2P NAT 穿透。
- `quicEndpoint`：启用 QUIC 隧道端点（`RELAY_QUIC_PORT`）时下发，支持 QUIC ↔ QUIC 及 QUIC ↔ WebSocket 透明混合桥接。

### 3.5 Built-in UDP STUN 与 QUIC 隧道（v2 可选传输层增强）

1. **内置 RFC 5389 UDP STUN**（`RELAY_STUN_PORT` / `--stun-port`，推荐 `3478/udp`）：
   - 响应标准 STUN Binding Request（`0x0001`），返回 `XOR-MAPPED-ADDRESS`（`0x0020`，兼容 IPv4 与 IPv6），静默忽略非 STUN 报文，零反射放大风险。
2. **QUIC 隧道端点**（`RELAY_QUIC_PORT` / `--quic-port`，推荐 `8443/udp`，ALPN：`octopus-relay-v2`）：
   - 客户端/主机仍先通过 `POST /v1/tunnels` 创建隧道 ID，再直连 `quic://<host>:<port>` 并打开一条双向流；
   - 首帧发送 4 字节小端长度前缀的 JSON 鉴权包 `{"tunnel":"...","role":"host|device","token":"oa1...."}`，服务端验证令牌与角色后回包 `{"ok":true}`；
   - 鉴权通过后该双向流直接切换为 4 字节小端长度前缀的数据帧转发流（与 `FramedStreamTransport` 一致），且支持**一端 QUIC、另一端 WebSocket 的混合配对**（例如桌面主机走 QUIC、移动端走 WSS）。

### 3.2 鉴权方式一：浏览器设备码（兼容所有版本 Octopus）

1. `POST /v1/auth/device`：客户端提交设备公钥与名称，返回 `deviceCode`、`userCode`（如 `WDJB-MJHT`）及 `verificationUriComplete`（未设 `RELAY_PUBLIC_URL` 时自动从请求 `Host` + `X-Forwarded-Proto` 推导）。
2. 机主在内置 Web 控制台（`/login` → `/device`）输入管理员密码并点击允许。
3. `POST /v1/auth/token`（`grantType: "device_code"`）：客户端用设备私钥对 `SHA-256("octopus-relay/1 login\n" ‖ deviceCode)` 签名换取：
   - `accessToken`：`oa1.<base64url(payload)>.<HMAC>`（15 分钟无状态令牌）
   - `refreshToken`：`or1.<deviceId>.<random>`（60 天单次轮换，超时重用旧令牌触发盗用检测并立刻踢出该设备）

### 3.3 鉴权方式二：Access Key 免浏览器直连（自建扩展）

1. `POST /v1/auth/key/challenge` → 返回一次性 32 字节随机数 `challenge`（base64，2 分钟有效，单次消费防重放）。
2. 客户端用设备私钥对 `SHA-256("octopus-relay/1 key-login\n" ‖ challengeBytes)` 签名。
3. `POST /v1/auth/key` 提交 `{ accessKey, challenge, deviceName, kind, publicKey, signature, platform, appVersion }`：
   - 定长比对 `accessKey`、消费 `challenge`、验签 `publicKey`，登记设备后直接返回**标准 `TokenBody`**。
   - 后续所有请求（刷新、退出、设备列表、隧道转发）与设备码登录完全共用同一套代码，协议零分叉。
4. **一键配置链接**：
   `octopus://relay?v=1&url=<urlencoded origin>&key=<urlencoded accessKey>`
   粘贴到 Octopus 桌面端或手机端自定义服务输入框即可自动解析地址与密钥并完成绑定。

### 3.4 中转数据面与设备列表（与官方完全一致）

| 端点 | 用途 |
|---|---|
| `GET /v1/me` | 返回当前机主信息 |
| `GET /v1/devices` | 列出所有已授权设备、实时 `online`、是否当前设备 `current` 以及 `passwordAccess` 能力标记 |
| `DELETE /v1/devices/{id}` | 移除设备并立刻吊销令牌、断开其控制连接（`4403`）与所有隧道 |
| `GET /v1/host`（WS） | 主机常驻控制连接：下发 32B `nonce` → 主机签 `SHA-256("octopus-relay/1 host\n" ‖ nonce)` 并携带初始 `features` 注册；支持运行中实时发送 `{"type":"features","features":[...]}` 更新能力；收到 `{"type":"connect","tunnel":"..."}` 时回拨隧道 |
| `POST /v1/tunnels` | 远程端提交 `{ hostDeviceId }`，服务端通知在线主机并返回 `201 { tunnel }` |
| `GET /v1/tunnel/{id}?role=host\|device`（WS） | 两端各连一条，服务端按 64 KiB 缓冲逐帧透明双向转发，任一端关闭则对端同步关闭 |
| `GET /healthz` / `GET /readyz` | 健康检查 |
